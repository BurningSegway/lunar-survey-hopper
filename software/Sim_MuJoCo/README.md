# Python MuJoCo jumper simulator

The supported simulator is the Python application in `jumper_sim/`, using
MuJoCo's interactive Python viewer and the model at
`build/Jumping_Robot.xml`. Its controls run the jumper's PID or LQR attitude
controller, jump/tilt behavior, and reaction-wheel management while the viewer
is open.

## Setup

MuJoCo 3.2.3 has a prebuilt wheel for Python 3.12. Create the project venv and
install the runtime and terrain conversion dependencies:

```sh
python3.12 -m venv --without-pip .venv
pip --python .venv/bin/python install -r requirements.txt -r requirements-terrain.txt
```

The MJCF uses a visual `build/terrain.obj` and a collision heightfield
`build/terrain_height.bin` (MuJoCo's float32 binary format; an 8-bit PNG, still
possible with `--heightfield NAME.png`, gave ~2 cm height steps that tilted the
ground facets by up to ~4 deg). Both are generated by `build/convert_usd.py` from
the moon surface in `build/Testing/Temporary/moon-surface/source/MoonSurface.zip`.

The moon surface download is tracked with Git LFS as `build/moon-surface.zip`
(run `git lfs install` once before cloning, or `git lfs pull` after). Extract
it into `build/Testing/Temporary/moon-surface/` (it holds `source/` and
`textures/`), then run the converter:

```sh
unzip build/moon-surface.zip -d build/Testing/Temporary/moon-surface
.venv/bin/python build/convert_usd.py
```

On Windows (PowerShell):

```powershell
Expand-Archive build\moon-surface.zip build\Testing\Temporary\moon-surface
.venv\Scripts\python.exe build\convert_usd.py
```

The moon surface terrain is
["Moon Surface"](https://sketchfab.com/3d-models/moon-surface-489dac88bfa4453fadac38d03fcd1de9)
by Giorgi Samukashvili, published on Sketchfab under a Creative Commons
Attribution (CC BY) license; the full download is available from that page.

By default the converter reads the OBJ inside that zip, turns it from Y-up to
Z-up and scales it from centimetres to metres (`--up y --scale 0.01`), giving
a 100 x 100 m crater field with about 5 m of relief. It centres the terrain
on the world origin, with the ground right below the robot's spawn point at
height 0, so the visual mesh sits at `pos="0 0 0"`. The heightfield has
401x401 samples (25 cm cells, `--resolution`). The visual mesh is drawn in a
plain colour, which shows the relief best. `--texture` also writes the
8192x8192 diffuse texture as `build/terrain_diffuse.png` (MuJoCo 3.2.3 reads no
JPEG); to use it, add a `texture` and `material` to the MJCF and give
`terrain_visual` that material.

The converter prints the `size` of `terrain_heightfield` and the `pos` of
`terrain_collision` for the MJCF; update those when the terrain changes. It
also reads USD (first mesh prim) and other OBJ files via `--input`.

`build/moon-surface.zip` is trimmed from the Sketchfab download to what the
converter uses: the OBJ (with its `.mtl`) in `source/MoonSurface.zip` and
`textures/Diffuse.jpeg`. The FBX/GLB copies, the compressed textures and the
normal and roughness maps are left out. The generated files and
`build/Testing/` are ignored by Git.

Loose objects (rocks) are removed: only the largest connected surface is
kept, because a heightfield cannot represent them and they never had real
collision. `--tiles N` (odd) repeats the terrain N x N around the original,
with step seams between copies. The collision is a heightfield; there is no
separate plane geom in the MJCF.

## Launch

Run from this directory:

```sh
.venv/bin/python -m jumper_sim --controller pid
```

Options:

- `--controller pid|lqr` selects the attitude controller (default: `pid`).
- `--model PATH` loads another compatible MJCF (default:
  `build/Jumping_Robot.xml`). It must provide the simulator's named root,
  reaction-wheel, jump, and tilt joints/actuators.
- `--track-target X Y` sets the ground position the lidar tracks during a
  jump's ascent. The tracked point is 0.15 m above the terrain
  there (`aim_height` in `FlightReferenceConfig`), so it is never in the air
  or below the ground; off the terrain the take-off ground height is used.
  Without it, a random target is chosen 2-20 m from the spawn
  (`RANDOM_TARGET_RADIUS` in `jumper_sim/app.py`) and printed as
  `[TARGET] ... --track-target X Y` so the run can be repeated.
- `--no-target` uses no target: no target object, and the lidar tracks a
  point 3 m ahead of the take-off point.
- `--scan-file PATH` is where the lidar point cloud is written (
  default: `pointclouds/target_scan.ply`). `--no-scan` turns scanning off.
  `--no-scan-window` keeps the file but does not open the live point cloud
  window.
- The lidar is the Livox Mid-360S on the side (used for development).
  `--lidar as-dt1` launches the other sensor under consideration, the Sony
  AS-DT1 under the bottom, with the robot facing its direction of travel in
  flight (see "Lidar option: Sony AS-DT1" below).
- `--spin` makes the robot spin slowly (45 deg/s) about the vertical in
  flight, with either lidar (for the AS-DT1 instead of facing travel); it
  stops 1 s before the predicted touchdown.
- `--lidar-fraction F` sets the fraction of the lidar's real point rate
  that is simulated (default: 1; for the Mid-360S 0.1 without an NVIDIA
  GPU); see "Lidar" below.
- `--smooth` simulates 3 % of the Mid-360S's point rate (6000 points/s) so
  the viewer runs without stutter on a CPU; `--lidar-fraction` overrides it.
  Measured over a Moon hop, stepping in the viewer's 8.3 ms slices: 1.7 % of
  the slices run over (95th percentile 7.3 ms) and the simulation needs half
  of real time, against 10 % of the slices at the default 10 % (5 % at 5 %,
  1 % at 1 %; without any lidar 0 %). The landing plane fit is a little
  noisier with fewer points (landing benchmark: touchdown misalignment median
  0.47 deg, p90 1.21, against 0.29 and 0.84 at 10 %), so use it for watching
  and the default for measurements.

## Controls

- `Space`: initiate a jump (release the springs for 0.4 seconds, then wind them back);
  while tipped over, attempt a recovery instead (see "Tipped over")
- `Backspace`: toggle Earth/Moon gravity without resetting the simulation (the
  simulation starts in Moon gravity)
- When the robot remains below the configured linear and angular speed limits
  (0.05 m/s and 0.05 rad/s by default) for one second, wheel speed references
  ramp toward zero while existing attitude references are retained. Motion
  resumes normal stabilization.
- `X`: disable reaction-wheel motor torque; press `C` to re-enable stabilization
- `C`: re-enable stabilization after disabling it with `X`
- `R`: reset the simulation, restore Moon gravity and point the camera back at
  the robot

The camera follows the robot (centred on it every frame, so it does not lag
or stutter when the robot moves fast). Rotating and zooming with the mouse
keep following; panning, or picking another camera, stops it until `R`. The
simulation runs in step with the wall clock and hands the viewer new state
at 120 Hz.

MuJoCo's viewer has its own Backspace reset shortcut. The simulator restores
the previous physics state when that default action occurs, then applies the
gravity toggle; use `R` when an actual reset is desired.

A white label above the robot, `h = ... m`, shows the height of its base
above where the base was when the robot last touched the ground (it appears
after the first touchdown, so not during the spawn drop).

The simulator streams telemetry over UDP to PlotJuggler at
`127.0.0.1:9870`. Open `PlotJuggler_Setup.xml` in PlotJuggler to load the
existing orientation and reaction-wheel plots. The stream includes current
roll, pitch, and yaw, their references, and X/Y/Z wheel speeds in rad/s.
Start PlotJuggler's UDP Server listening on port `9870` before launching the
simulator.

## Sensor cube model and LQR (report chapters 4-5)

`--controller lqr` is the LQR of the project report with the integral
reference tracking of its MATLAB script (`angular_reference_integral.mlx`),
on the report's model of the sensor cube; the simulated robot is fitted to
the same model.

**Model** (`jumper_sim/cube_model.py`). The cube is a gyrostat: state
`x = [q1 q2 q3 q4 wx wy wz]` (attitude quaternion, scalar last, and body
rates), wheel speeds `Omega` relative to the body. The input is the wheel
motor torque `u = tau` (the body gets `-tau`). Each wheel spins up as
`J_w,i (Omega_dot_i + w_dot_i) = tau_i`; putting
`J_w Omega_dot = tau - J_w w_dot` into the gyrostat equation (4.8) gives
`dynamics()`, `x_dot = f(x, u)`: `q_dot = 1/2 S_q q` and
`w_dot = (J_c - J_w)^-1 (-tau - S(w) (J_c w + J_w Omega))`, free flight
(`wheel_accelerations()` gives `Omega_dot`). `jacobians()` gives A and B
anywhere; `linearize(Omega_hat)` gives the reduced `A_r`, `B_r` about
`q0 = [0 0 0 1]`, `w0 = 0` with the wheels at `Omega_hat` (q4 stripped, 5.1).
At the report's `Omega_hat = 0`, `A_r`'s rate block is zero and
`B_r = [0; -diag(1 / (J_c,i - J_w,i))]`; with spun wheels the rate block is
`(J_c - J_w)^-1 S(J_w Omega_hat)`. `Omega` is not a state: the total momentum
is conserved, so `w` and `Omega` cannot be controlled independently.

The values are the final design's, `SENSOR_CUBE`: CAD
`J_c = diag(0.07066, 0.07067, 0.07333) kg*m^2` (whole robot, wheels locked,
about its CoM), `J_w,i = 0.004422 kg*m^2`, cube 3.3 kg (placeholder), plus
the jump springs (below).

**Controller** (`LqrController` in `jumper_sim/controller.py`), the script's
9-state LQI. The plant `x_r = [q1 q2 q3 wx wy wz]` is augmented with the
integrated tracking error `x_I` (`x_I_dot = q_v - r`, the script's eq. 25):
`A_aug = [[A_r, 0], [C, 0]]`, `B_aug = [B_r; 0]`, `C = [I 0]`, and
`u = tau = -K_bar [x_r; x_I]` with `K_bar = R^-1 B_aug' P` from the algebraic
Riccati equation (5.6-5.7), solved in `solve_continuous_are` (matrix sign
function, no dependencies).

- **Reference tracking.** The script adds `N r` with `N = N_u + K N_x` from
  `[[A_r, B_r], [C, 0]] [N_x; N_u] = [0; I]` (`tracking_feedforward()`). For
  this plant `N_x = [I; 0]` and `N_u = 0`, so `-K x_r + N r = -K [q_v - r; w]`:
  the error to the reference. The controller is given that error directly,
  as the error quaternion's vector part to the reference attitude (equal to
  `q_v - r` near level, and still right at the hop reference's 60 deg tilt),
  plus the rate error to the reference's rate, so a turning reference is
  followed without lag.
- **Weights** (Bryson's rule, `LqrLimits`, the script's): 15 deg attitude
  error (weighed as `angle/2` on the quaternion), 60 deg/s rate, 5 deg*s
  integral, 10 rev/s^2 wheel acceleration. The script's input is the wheel
  acceleration; ours is the motor torque `tau_i = J_eff,i Omega_dot_i`
  (`J_eff,i = J_w,i (J_c,i - J_w,i) / J_c,i`), so R is weighed on 0.26 N*m,
  which gives the script's closed loop exactly (poles -3.1 +- 2.0j, -1.6;
  `K_bar / J_eff` is the script's 770.5 / 126.1 / 720). That bound is only a
  weight: the torque is clipped at the 1.95 N*m motor limit.
- **Anti-windup** (not in the script): an axis only integrates while its
  error is below 5 deg (`integral_zone`), and its integral's torque is
  clamped at 0.8 N*m (`integral_torque_limit`); the simulator empties it at
  every lift-off and touchdown. `None` for both gives the script's pure
  integrator.
- As in the report, the model is linearised with the wheels at rest
  (`Omega_hat = 0`): one constant, per-axis gain, solved once. Optionally
  (`schedule_wheel_speeds=True`) the gain is re-solved whenever the measured
  wheel speeds move 2 rad/s, so it matches the momentum the wheels hold. The
  torque goes to the motors as it is (ODrive torque mode), clipped to the
  motor limit, plus the bearing-friction feedforward.

**Simulated plant.** `build/fit_robot_model.py` writes `SENSOR_CUBE` and the
springs into `build/Jumping_Robot.xml`: wheel inertias, the base's mass and
full inertia tensor so the whole robot in flight is exactly `diag(J_c)` (no
products of inertia), the jump joint and the spawn height. Rerun it after
changing the values in `cube_model.py`; tests check that the MJCF matches.
Integrating the report's `f(x, u)` alongside MuJoCo (tumbling, spun wheels,
varying torques) tracks the body rate within 0.002 rad/s and the attitude
within 0.1 deg over 0.3 s.

**Measured** (same 4.2 kg plant). Free flight, run over 8 s from 200 m
(the benchmark's 2 s window is too short for these weights): every scenario
settles into 2 deg in 0.65-2.9 s with no steady error, against 0.16-0.58 s
for the previous LQR without integrator (9 deg / 1.6 rad/s / full motor
torque); it saturates less (<= 2 % against <= 13 %) and spins the wheels
less. The two scenarios with spun wheels are the slowest (2.5-2.9 s: the
fixed gain does not model the wheels' coupling). Without the anti-windup the
large tilts wind the integrator up: 1.7-4.2 s, 9-34 % more integrated error.
Landing benchmark: median 0.32 deg, p90 1.33 deg off the ground at
touchdown (previous LQR 0.29 / 0.84); from 3 m 0.76 deg median (0.41),
from 10 m 0.20 deg (0.32). On the target-tracking Earth hop test it is
3.0 deg off at the apex and at most 3.0 deg in the descent (previous LQR
0.2 deg at the apex; pure integrator 5.9 deg in the descent). The reference's
rate is followed up to 1 rad/s (`REFERENCE_RATE_FEEDFORWARD_LIMIT`): faster,
such as the 180 deg/s slew that catches up at lift-off, counts as error.

## One hop process for both controllers

PID and LQR run the same hop process, so they can be compared on equal
terms: contact gating, the hop phases and attitude reference, leaning
towards the target, the target object and scan, and the lidar landing
reference below all apply to both. Both regulate the body-frame quaternion
error to the reference attitude; only the control law differs, plus wheel
friction compensation and the rate error to the moving reference, which only
the LQR uses (the PID gains were tuned with bearing friction acting as
damping, and on the raw body rate). The PID tracks the target less tightly:
1.2 deg off at the apex of the Earth hop test (6.4 deg in the descent)
against 3.0 deg (3.0) for the LQR, which is softer but integrates.

## Contact gating

The controller only controls attitude in flight. From the first step any part of the
robot touches the terrain it is "in contact": attitude control stops, the
integrator resets and the wheel-rest ramp bleeds the wheels' momentum into
the ground (this replaces the stationary-for-1-s rest trigger).
It is airborne again after 60 ms without contact (`FLIGHT_DEBOUNCE`), so
rocking on the legs or skidding is one contact phase; at lift-off the controller
resumes with a fresh integrator and the current heading as yaw reference.
Disable with `JumperSimulation(..., contact_gating=False)`.

## Hop phases and attitude reference

A hop runs through five phases; every behaviour switches on them, so none
acts in a phase it is not meant for. Code: `jumper_sim/flight_phase.py`.

| Phase | Starts when | What happens |
|---|---|---|
| GROUND | still (~1 g, body rate < 0.2 rad/s) for 0.5 s after landing | leaning towards the target (next section); wheels spin down |
| TAKEOFF | jump command (`Space`) | legs held as they are; after lift-off the lift-off attitude is held |
| ASCENT | airborne and 0.5 m above the standing height | the robot's bottom tracks the target and it turns to face its travel (AS-DT1); lidar scans |
| DESCENT | apex (vertical velocity turns negative) | on a jump, target tracking goes on for half the ascent's time; then the reference goes back to level, then to the landing-plane fit at the predicted landing spot, still facing its travel; lidar scans |
| LANDING | touchdown near (landing plane < 1 m below or < 0.3 s away), or ground contact | the landing plane keeps updating until impact; legs straight |

- A hop that peaks below 0.5 m skips ASCENT; a jump that does not leave the
  ground returns to GROUND after 0.5 s.
- Bounces stay in LANDING, so they never track the target or lean.
- Leaving the ground without a jump (pushed, rolled off a rim) is DESCENT.
- The program starts in DESCENT (the robot may be in the air) and settles to
  GROUND; so does a reset (`R`).
- Attitude control itself is still switched by ground contact (next section
  up): off from touchdown, on 60 ms after lift-off.

The vertical velocity is integrated from the accelerometer (free flight reads
~0 g on the way up and down, so the sign of the integrated velocity, not the
acceleration itself, marks the apex), and reset whenever the robot stands
still. Ground contact still comes from the simulator. Phase changes are
printed to the console (`[PHASE] ...`, `[FLIGHT] ...`).

Attitude reference per phase (`jumper_sim/flight_reference.py`): in ASCENT,
on a jump, the robot's bottom (body -z, inside the lidar's field of view)
is pointed at the track target and follows it as the robot
moves (red sphere and line of
sight in the viewer; tilt capped at 60 deg). It keeps tracking for the
first half of the ascent's time (lift-off to apex) into the descent, since
the descent takes about as long (a criterion from the predicted landing spot
is planned instead); the red line of sight stays in the viewer for as long
as the target is tracked. Then the reference moves back towards level, and as
soon as the ground at the predicted landing spot has been fitted, to its
plane ("Landing reference from the lidar"), which keeps updating through
LANDING until the moment of impact. The reference slews at most 180 deg/s, so
the controller never sees a reference step.

### Leaning towards the target

On the ground, with a track target (set or random, not `--no-target`), the robot leans
its body axis towards the target so the next jump heads that way (the jump
spring pushes along the body axis). The lean is 3 deg near the target (so a
hop always moves towards it, and close by goes over it) growing to 8 deg at
30 m and beyond; within 0.5 m it stands upright.

It is closed loop on the IMU attitude: the error between the wanted and the
measured tilt of the body axis is integrated (0.5 s time constant) into a leg
plane, and each leg is shortened (its motor pulls against the leg's shock
spring) to that plane: the leg closest to the lean direction most, the
furthest not at all. Because it uses the measured attitude, it also cancels
slopes. Rules that keep it out of other phases:

- it only acts in GROUND, and only adjusts while the robot is still (body
  rate < 0.3 rad/s);
- in TAKEOFF the legs are held as they are;
- from lift-off until the robot is back in GROUND the legs are straight;
- no leg is shortened by more than 10 cm (further and the body box would
  touch the ground); at that limit the whole leg plane is scaled down, so on
  a slope the lean can stay short of the wanted one;
- on ground tilted more than 20 deg it does not lean.

The console prints e.g. `[AIM] Target 40.0 m away: leaning 7.0 deg towards
it.`, with `(wanted ...; legs at their limit)` when the legs ran out of
travel. Tuning: `JumpAimConfig` in `jumper_sim/jump_aim.py`. The max lean is
kept at 8 deg because launches at 10-14 deg tumbled: the jumping foot slams
into the ground on release (see the open items).

### Target object

At the track target (`--track-target X Y` or the random one) a bright orange
Stanford Bunny (0.3 m tall:
`build/target_bunny.obj` is 1.5 m, scaled by 0.2 in the MJCF; Stanford
University Computer Graphics Laboratory, taken from MuJoCo's model collection)
rests on the terrain at (X, Y), tilted to a plane fitted to the ground under
it so it neither floats nor sinks in on slopes. The lidar sees it (an
exact ray/mesh test added to the terrain ray caster, `MeshRayCaster` in
`jumper_sim/ray_casting.py`), so it appears in the point cloud and in
landing-plane fits near it; the robot collides with its convex hull. The
robot aims its bottom at the middle of the bunny (0.15 m above the ground). With `--no-target` it is hidden below the terrain.

### Tipped over

On the ground (GROUND), when the body is tilted more than 60 deg, the robot
counts as tipped over: all four legs are pulled in to the end of their
stroke, leaning is off, and the console prints `[TIPPED]`. Below 45 deg it
is upright again.

Pulling the legs in does not right the robot by itself. On the ground,
nothing the robot has can (tested in Moon gravity with the robot lying on
its side):

- full reaction-wheel torque towards upright: the motor gives 1.62 N*m, the
  robot needs 1.46 N*m just to start tipping over its edge, and the wheel
  reaches its speed limit within ~0.3 s; spinning a wheel up first and then
  torquing the other way doubles that time, which rocks the body up ~10 deg;
- spinning a wheel up to full speed, then braking it (as the Cubli does):
  0.45 N*m*s gives the body ~0.27 J, ~0.6 J is needed to get over the edge
  (the motor brakes too slowly to do better);
- the legs: they slide along body z, which is horizontal when the robot lies
  on its side, so they only push along the ground. A kick (pull in, release)
  rolls the robot further over; even the full 1000 N motor push did not help.

**Space while tipped** therefore attempts a recovery in the air
(`jumper_sim/recovery.py`):

1. for 0.15 s the wheels torque the body away from upright, into the ground;
   this does nothing to the body but spins them up;
2. the jump spring is released. The foot points sideways, but it catches the
   ground often enough to throw the robot up;
3. in the air the attitude controller aims for level (keeping the heading)
   instead of the hop reference. Because the wheels start spun up the other
   way, they can use their whole speed range to swing the body upright.

The console prints `[RECOVERY] Upright.` or `[RECOVERY] Still tipped (...)`.
Each attempt starts from wherever the last one left the robot, so pressing
Space again is worth it. Measured (on the old 6 kg model with the old
spring, not yet redone for the 4.2 kg cube) on 16 terrain spots x 4 sides in
Moon gravity, via the Space key: upright after one attempt 41/54 and 40/55,
after up to three 51/54 and 54/55. In Earth gravity the hop is too short
for this: 0/57. Rocking the body up before releasing the spring, or
extending the legs, made it worse (see the module docstring). The attempt
needs the wheels (not after X; press C first), and it neither tracks the
target nor adds to the point cloud.

### Lidar (Livox Mid-360S)

The robot's only exteroceptive sensor is a Livox Mid-360S stand-in
(`jumper_sim/lidar.py`, 265 g), the one used for development on the +x side face, flush with the bottom (site
`lidar`). Its rotation axis points out of that face, tilted 22.5 deg down.
It sees a band all the way round that axis (-7..52 deg elevation), so
straight down (body -z) is in the middle of the band: the robot can point
its bottom straight at the target, and it sees the ground below it. The
blind cone (38 deg around the axis) points out and slightly down from that
face. It scans while the robot is airborne; its points feed the
landing-plane reference (below) and the point cloud. Rays are not blocked by
the robot itself (on the real robot the legs and foot would shadow some).

| | Livox Mid-360S (datasheet) |
|---|---|
| field of view | band 38-97 deg off its axis, all round; blind cone of 38 deg around the axis |
| point rate | 200k/s (first return) |
| range (10 % reflectivity) | 0.1-40 m |
| precision (1 sigma) | 2 cm range (4 cm within 1 m), 0.15 deg |

The 40 m is its typical range at 10 % reflectivity (about that of regolith);
it cuts off at 100 m on brighter surfaces. Its 0.1-0.2 m returns are
"reference only" in the datasheet; they are kept here with the 4 cm noise.
Range noise does not grow with distance as stereo noise does. Points are
placed with the true pose at each 10 ms batch; on the robot that is the IMU
de-skew of Livox's per-point timestamps.

The directions are Livox's own recorded non-repetitive scan pattern (from the
`mujoco-lidar` package), played back in time order at the real rate. It
sweeps the -7..52 deg elevation band about every 50 ms, so a single 10 ms
batch covers only part of it. With `--lidar-fraction` below 1, every 1/F-th
recorded point is cast, so the pattern still advances in real time.

The rays are cast on the GPU with NVIDIA Warp (`jumper_sim/gpu_ray_caster.py`:
the same terrain triangles and target mesh as the numpy caster in
`jumper_sim/ray_casting.py`, identical hits, ~80x faster), so the full point
rate is simulated. Without an NVIDIA GPU the numpy caster is used and only
10 % of the points are cast (the full rate runs at about real time but
stutters: 76 % of the viewer's 8.3 ms slices run over; `--smooth` casts 3 %).
`--lidar-fraction F` overrides either default. Measured on Moon hops
(3 targets, 8.4 s of flight each, side mount, landing reference included):

| caster, fraction | points per hop | within 0.3 m of the bunny | flight speed |
|---|---|---|---|
| CPU, 10 % | ~64-71k | 16-55 | 0.5-0.6x real time |
| GPU, 100 % | ~640-710k | 142-465 | 2.1-2.4x real time |

About half the side mount's band looks at the sky, so it returns fewer
points than the bottom mount did (~943k per hop); the target gets about as
many (bottom mount: 178-454).

A wide-field lidar spreads its points over everything it sees, so a 0.3 m
object 5-20 m away gets few of them. (Before choosing the Mid-360S, a Livox
Avia, 70.4 x 77.2 deg cone on its axis, put 7.2k-15k points near the target
on the same hops, ~30x more; and the earlier RealSense D435 stand-in cast
rays only towards the target.)

### Lidar option: Sony AS-DT1

The other sensor under consideration, a Sony AS-DT1 stand-in
(`jumper_sim/lidar.py`; 34 g, 29 x 29 x 31 mm, a fifth of the Mid-360S's
weight): a solid-state dToF (SPAD) lidar that measures the same 24 x 24 grid
every frame. It scans while the robot is airborne; its points feed the
landing-plane reference (below) and the point cloud. Each 15 fps frame (576
points) is cast at once, from that frame's pose. Rays are not blocked by the
robot itself.

It sits on site `lidar_down` under the bottom face, its axis tilted 10 deg
from body -z towards body +x. Body -z, which the robot points at the target
on the way up, stays 5 deg inside its 30 deg view. Since it does not scan on
its own, the robot's heading does the job:

- **Facing travel (`--lidar as-dt1`):** in ASCENT and DESCENT the robot turns about
  the vertical (at most 90 deg/s, 90 deg/s^2) so body +x, and with it the
  lidar's tilt, faces its horizontal velocity: the lidar looks ahead, where
  the robot will land. Turning does not move body -z, so target tracking is
  unaffected. Straight up or down (< 0.2 m/s horizontally) it keeps its heading.
- **`--lidar as-dt1 --spin`:** it spins slowly (45 deg/s, 8 s a turn) instead, sweeping the
  lidar round a cone ~25 deg around body -z. The spin stops 1 s before the
  predicted touchdown, keeping the heading reached. More ground is covered,
  but the landing spot is seen only part of the time.

Both live in `FlightReferenceConfig` (`face_travel`, `spin`, rates).

| datasheet | modelled as |
|---|---|
| HFoV 30 deg or more (VFoV not given) | 30 x 30 deg (square pixels assumed) |
| 576 points (24 x 24), 30 fps; 15 fps in max-range mode | 8640 points/s, 15 fps |
| 20 m outdoor, 40 m indoor (50 % reflectivity, centre) | 20 m |
| accuracy +-5 mm at 10 m, distance resolution 25 mm | 5 mm (1 sigma) noise, ranges rounded to 25 mm |
| min range, angular precision: not given | 0.1 m, none |

Regolith reflects ~10 %, and the sensor will see full sunlight with no
atmosphere, so the real range on the Moon is likely well under 20 m.

### Lidar point cloud

From lift-off to touchdown of every jump (not recovery hops), every lidar
point is added to a point cloud (`jumper_sim/pointcloud.py`), so it holds the
target as well as everything else the lidar saw, e.g. the landing area. It is
a binary PLY with `x y z` (m, world), `jump` (jump number in this run), `t`
(sim time) and `range` (lidar-to-point distance, m) per point. CloudCompare,
MeshLab and Open3D read it.

- The file is emptied when the program starts, so each run makes a fresh
  cloud.
- Every jump of the run adds to it: jump, press R, and jump again. The file
  is rewritten at each touchdown, and the console shows
  `[SCAN] Jump n: +k lidar points ...`.
- A full-rate cloud is large: ~21 MB per hop. Rewriting it takes ~30 ms
  per hop already in it (150 ms after 5 hops).
- Where each scanned jump touched down (the ground under the robot at first
  contact) is written at touchdown to `target_scan.touchdowns.json` next to
  the cloud (`[{"jump": n, "position": [x, y, z]}, ...]`; read it with
  `jumper_sim.pointcloud.read_touchdowns`), and the console shows
  `[SCAN] Jump n touched down at (x, y, z).`
- Cyan dots in the viewer show a sample of the cloud.
- A live Open3D window (separate process) opens at start-up and redraws
  whenever the file changes, i.e. at every touchdown. Points are coloured by
  jump, the track target is a small red sphere (3 cm, unless `--no-target` is given),
  points within 0.3 m of it are drawn white and larger so the target is easy
  to find, each jump's touchdown spot is a labelled green sphere,
  and axes mark the origin. The view fits the cloud once; after that your
  mouse view is kept (R refits, Q/Esc closes). Run it on its own with
  `.venv/bin/python -m jumper_sim.cloud_viewer pointclouds/target_scan.ply`.
  It needs `open3d` (in `requirements.txt`); without it the simulator says
  so and carries on.
- Points are placed with the robot's true pose at capture. On the robot this
  needs odometry/localisation.

Reading the cloud in Python:

```python
from jumper_sim.pointcloud import read_ply
cloud = read_ply("pointclouds/target_scan.ply")  # fields x, y, z, jump, t, range
```

## Landing reference from the lidar

The landing reference uses every lidar point of the current jump
(`jumper_sim/landing_reference.py`), so ground seen earlier in the hop
counts too:

1. while airborne, each lidar batch goes into a ground map of the jump
   (0.5 m grid; emptied when a jump starts);
2. every 50 ms during descent (or, without the hop reference, whenever
   airborne), the robot's ballistic trajectory (position, velocity, gravity)
   is followed to where the base first comes within 0.3 m of the mapped
   ground: the predicted landing spot;
3. up to 1000 of the jump's points (an even subsample) within 0.5 m of that
   spot are fitted to the area-averaged ground plane, with outlier
   rejection and an uncertainty estimate;
4. the fits are fused in a small Kalman filter that keeps updating until the
   moment of impact (it used to freeze when touchdown was < 1 m or < 0.3 s
   away; `freeze_near_touchdown` restores that); a near touchdown starts
   LANDING. The controller holds body z along that plane
   normal (clamped to 20 deg) with the usual yaw reference. Nothing updates
   in contact; a jump resets the reference to level. PlotJuggler's
   `roll_ref`/`pitch_ref` show it.

In the viewer: the disc is the latest fit at the predicted landing spot
(orange = it updated the reference, grey = not used or held in contact), the
green arrow is the reference normal, and the blue dots are a sample of the
lidar points used.

Measured (`landing_benchmark`: 36 thrown Moon hops onto 1-17 deg slopes,
5 m long, apex 3/6/10 m above the spot, attitude disturbed by up to 15 deg;
misalignment of body z to the true ground plane at touchdown):

| reference | median | p90 | max |
|---|---|---|---|
| land level | 9.84 deg | 16.38 deg | 16.79 deg |
| RealSense D435 stand-in, disc below the robot (as of the last commit) | 2.28 deg | 10.35 deg | 15.78 deg |
| Mid-360S on the bottom facing down (blind straight below) | 0.35 deg | 0.96 deg | 2.17 deg |
| Mid-360S on the side, 22.5 deg down, freezing near touchdown | 0.35 deg | 1.28 deg | 4.72 deg |
| **Mid-360S on the side, updating until impact (current)** | **0.23 deg** | **1.05 deg** | **4.72 deg** |
| Mid-360S, freezing near touchdown, `--spin` | 0.29 deg | 1.09 deg | 12.82 deg |
| AS-DT1 under the bottom, facing straight down | 1.19 deg | 9.47 deg | 13.59 deg |
| AS-DT1 facing straight down, spinning | 1.29 deg | 9.78 deg | 16.82 deg |
| AS-DT1 tilted 10 deg, spinning (`--lidar as-dt1 --spin`) | 0.76 deg | 9.73 deg | 16.66 deg |
| AS-DT1 tilted 10 deg, facing travel (`--lidar as-dt1`) | 0.57 deg | 5.07 deg | 12.27 deg |

The camera only saw the ground straight below, which on a hop is not where
the robot lands, and from 3 m apex it had too few usable frames (median
6.5 deg). The side mount's two worst hops (4.6-4.7 deg) are low (3 m apex)
hops onto 15-17 deg slopes: its band leaves part of the landing disc unseen,
depending on the heading, and the fit is biased by it.

The bottom mount could not see where it landed when falling straight down
from rest (pushed off a rim, or the contact benchmark's drops): it landed
level, misaligned by the slope (1-17 deg), and tipped over in 4 of 12 drops.
The side mount sees below itself: those drops land 0.11-0.41 deg off the
ground plane, none tipped; updating until impact (instead of freezing 1 m /
0.3 s before) brings that to 0.01-0.23 deg, still none tipped. The hop from
the spawn, which also tracks the target for half its ascent time into the
descent now, lands 0.37 deg off and stays upright (before: 0.17 deg, then
tipped; camera: 3.15 deg). Wheel peak 17.1 rev/s (before 16.2).

The AS-DT1's 30 deg view covers little ground, so what matters is where it
looks during the descent. Facing straight down it saw the landing spot of a
hop late; spinning spreads its points round a cone, so the spot is in view
only part of the time (a 6 m hop onto 17 deg got 6 fits and landed 4.5 deg
off; the wheels peaked at 20 % and the spin was stopped as planned, it is
coverage). Facing travel keeps the tilted view ahead on the landing spot:
by apex (median), 3.15 deg from 3 m, 0.24 deg from 6 m and 0.35 deg from
10 m (spin: 6.39 / 0.34 / 0.23; facing down: 4.92 / 0.80 / 0.34). Low (3 m)
hops onto 9-16 deg slopes are still its weak spot (up to 12 deg), with only
~16 fits. In the contact benchmark's vertical drops it lands 0.12-2.34 deg
off and none tip (Mid-360S: 0.11-0.41 deg, none; AS-DT1 facing down:
up to 4.7 deg, 3 tipped).

Points per hop from the spawn (8.5 s of flight; targets 3, 8 and 15 m away;
bunny = within 0.3 m of the target, above the ground; landing disc = within
0.5 m of the touchdown point):

| lidar | points | on the bunny | landing disc | ground covered (0.5 m cells) |
|---|---|---|---|---|
| **Mid-360S (side, current)** | **603-674k** | 166 / 102 / 47 | 6.1-6.5k | 2345-2932 m^2 |
| AS-DT1, `--lidar as-dt1 --spin` | 53-73k | 40 / 23 / 4 | 1.3k | 302-362 m^2 |
| AS-DT1, `--lidar as-dt1` (facing travel) | 56-73k | 49 / 16 / 7 | 3.0-3.2k | 179-283 m^2 |

The AS-DT1 casts ~9-11x fewer points, nearly all of which hit (8640/s); it
puts about a third as many on the target, half as many in the landing disc
(the spin: a fifth) and covers ~10x less ground.

- The trajectory uses the true position and velocity; on the robot they
  come from the state estimate.
- `jumper_sim/landing_reference.py`: ground map, landing prediction, plane
  fit, filter and reference attitude; written to run unchanged on the robot.
- `jumper_sim/visualization.py`: the viewer overlay.
- Tuning: `LandingReferenceConfig` (disc radius, max points, fit period,
  touchdown clearance, max tilt, filter noise, near-touchdown rules).

## Terrain

The terrain is a 100 x 100 m moon crater field (about 5 m of
relief, robot spawn at the centre on ground at height 0); see Setup.

The terrain contact (`terrain_collision` in the MJCF, with `priority="1"` so
it governs the legs' and body's contacts with the ground) is firm and
overdamped (`solref 0.005 1.5`, `solimp 0.9 0.95 0.01`), friction 0.7. An
earlier, softer sand-like contact (`solref 0.03 2`) let Moon landings push the
legs 8-17 cm into the ground, where they could stay stuck; now they go in
about 3 cm at most.

The jumping foot has its own contact: a 4 cm sphere, even firmer
(`priority="2"`, `solref 0.002 1`, the sand's friction), so the spring pushes
off the surface instead of sinking into the sand and being ejected. The foot
is round because a flat cylinder on flat ground touches at a single rim
point, which spun the robot at take-off.

## Jump springs

The foot is pushed by four compression springs in parallel (fjedre.dk 13760:
piano wire, 54 mm outer diameter, free length 335 mm, max. loaded length
77.8 mm, 1.67 N/mm, 224 g; `JUMP_SPRING` in `jumper_sim/cube_model.py`):
6680 N/m together, wound to full compression before each jump (257.2 mm,
1718 N, 221 J). Where the springs sit and how long they are is not modelled
(for now): the wound foot sits at the bottom of the cube, `Space` releases it
to the springs' full stroke, and 0.4 s later the wind-up (1.25x the wound
force) pulls it back. The joint has light damping (2 N*s/m), stiff ends of
stroke, and a third of the springs' mass moving with the foot (armature). The
robot weighs 4.196 kg (3.3 kg cube + 0.896 kg springs).

Measured on 5 spots: about 1.65 m apex on Earth (1.5-2.1 m) and 9.2 m on the
Moon (7.7-11.7 m), take-off at 5.2-6.4 m/s. Starting from the bottom of the
cube, the foot falls 12.75 cm before it reaches the ground, and the springs
spend much of their energy on it (all 221 J in the robot would give
10.3 m/s; a foot wound flush with the leg tips reached 9.8 m/s, ~4.7 m Earth
/ ~28 m Moon, but landed on its rigid stop and tipped 3 of 12 benchmark drops).
Take-off spin is mostly below 2 rad/s (5.9 rad/s at one Earth spot).

## Benchmarks

- `python -m benchmarks.lqr_benchmark --label NAME [--compare OTHER]`:
  free-flight attitude recovery; `python -m benchmarks.plot_results A B ...`
  plots saved runs.
- `python -m benchmarks.landing_benchmark --label NAME`: hops thrown onto
  sloped terrain, touchdown misalignment with and without the lidar landing
  reference.
- `python -m benchmarks.contact_benchmark --label NAME`: drops with bounces
  and a hop from the spawn point, with and without contact gating.

Contact behaviour differs between MuJoCo versions (on 3.2.3 the jump spring
launches the robot at ~5 m/s, on 3.16 at ~1 m/s), so run the contact and
landing benchmarks on the pinned version.

## Tuning

Edit `ReactionWheelTuning`, `PidGains`, and `LqrLimits` in
`jumper_sim/controller.py` to change the PID gains, wheel speed/acceleration
limits, stationary detection thresholds and duration, wheel-rest behavior,
wheel friction, and the LQR's physical tuning limits (Bryson's rule) and
anti-windup.
`LqrController` also takes `schedule_wheel_speeds` and `relinearize_step`. The robot's design values (J_c, J_w,i, masses, jump
springs) live in `jumper_sim/cube_model.py`; the LQR and the motor limits use
them directly, and `build/fit_robot_model.py` writes them into the MJCF. Keep
`wheel_viscous_friction` consistent with the wheel joints' damping.
